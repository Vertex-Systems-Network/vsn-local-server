## Amendment findings

The following 22 findings are approved for application. Their category and priority are part of the contract.

### P0 — apply before resuming 03.11 product implementation

1. **CORRECTION — package-neutral canonical-state resolution.**
   Remove active-package hardcoding such as PKG-02 tracker references from generic AI governance. Resolve the active package and active certification tracker from live canonical state. Historical audit baselines remain historical.

2. **CORRECTION — repair and guard all live human-readable status projections.**
   Bring `.ai/README.md`, `docs/MASTER-EXECUTION-PLAN.md` live/current-state sections, README current-package state, and any equivalent live projection into agreement with canonical state. Expand Repository Governance so stale projections fail closed.

3. **COMPLETION — durable current-work/checkpoint layer.**
   Add a lightweight machine-readable active-work/checkpoint record instead of a duplicate multi-file Memory Bank. It records snapshot state, branches/PRs, stage, last verified action, blockers, gates, and next safe action. It is explicitly non-authoritative until refreshed from live canonical sources.

4. **COMPLETION — existing-project adoption audit contract.**
   Define reusable plan-to-repository and repository-to-plan audit states:
   `NOT_STARTED`, `PARTIALLY_IMPLEMENTED`, `IMPLEMENTED_NOT_VERIFIED`, `VERIFIED`, `DIFFERS_FROM_PLAN`, `UNKNOWN`;
   and documentation states:
   `DOCUMENTED`, `PARTIALLY_DOCUMENTED`, `UNDOCUMENTED`, `OBSOLETE`, `UNKNOWN_PURPOSE`.

5. **COMPLETION — project-state and capability ledger.**
   Standardize project classifications:
   `GREENFIELD`, `PLANNED_EXISTING_PROJECT`, `ACTIVE_EXISTING_PROJECT`, `PRODUCTION_PROJECT`, `LEGACY_OR_MIGRATION`, `RECOVERY`.
   Record actual available capabilities and privilege level; unknown/unavailable capability must not be assumed.

6. **HARDENING — separate canonical acceptance state from live WIP.**
   Keep canonical DONE/READY evidence distinct from in-flight planning/implementation/reconciliation lanes. Add a durable WIP registry/checkpoint rather than projecting branch work as canonical acceptance.

7. **CORRECTION — historical documents must identify themselves as historical.**
   Old audit/blueprint documents containing obsolete active-task/main references must be marked `HISTORICAL BASELINE — NOT LIVE EXECUTION STATE` and link to current canonical sources.

### P1 — engineering-contract hardening

8. **COMPLETION — gap classification.**
   Add `CORRECTION`, `COMPLETION`, `HARDENING`, `OPTIMIZATION`, `NEW_PRODUCT_SCOPE`. `NEW_PRODUCT_SCOPE` requires explicit approval and must not be auto-implemented.

9. **HARDENING — machine-readable approval scope.**
   Record approval scope (`TASK`, `MODULE`, `MILESTONE`, `PHASE`, `PROJECT`), approval reference, inherited existing authorization, and reapproval triggers. Do not retroactively block clearly authorized existing work.

10. **COMPLETION — deeper module/option specification contract.**
    For applicable product modules require identity, interfaces, options/settings, permissions, data, workflows, integrations, security, error/loading/empty/disabled states, responsive/accessibility behavior, testing, rollback and acceptance. Non-applicable sections require rationale rather than fabricated detail.

11. **HARDENING — first-class negative requirements and abuse cases.**
    Add `must_not`, abuse cases and forbidden cross-boundary behavior to feature contracts and map important negative rules to tests/evidence.

12. **HARDENING — small-batch mutation budget.**
    Preflight records expected changed files/modules/shared surfaces and a reasonable scope/diff budget. Unexpected expansion requires `STOP_AND_REASSESS`.

13. **HARDENING — universal parallel-safety classification.**
    Add `PARALLEL_SAFE`, `COORDINATED_PARALLEL`, `SERIALIZE`, `BLOCKED`, including named shared surfaces and collision rules. Package-specific concurrency limits remain authoritative.

14. **COMPLETION — FAST GATE / FULL GATE.**
    Formalize targeted fast checks during implementation and broader full gates at milestone/release boundaries. Fast gates never substitute for required final acceptance.

15. **HARDENING — baseline-failure and flaky-test policy.**
    Record pre-existing failures as `BASELINE_FAILURE`. Do not attribute them to unrelated work. A flaky test is a defect; repeated reruns until green are not acceptable evidence.

16. **COMPLETION — universal Definition of Done.**
    DONE requires applicable implementation, acceptance, security/data/error handling, integration, docs/checkpoint, known limitations and rollback/recovery understanding. Otherwise use `PARTIALLY_COMPLETE`.

17. **HARDENING — review provenance.**
    Label review as `SELF_REVIEW`, `INDEPENDENT_AI_REVIEW`, `HUMAN_REVIEW`, or `REQUIRED_EXTERNAL_REVIEW`. Self-review cannot be represented as independent review.

### P2 — operational/release maturity

18. **COMPLETION — operational readiness block.**
    Plans define applicable structured logging, audit logging, request/correlation IDs, health, metrics, alerts, job monitoring, troubleshooting and sensitive-log policy.

19. **COMPLETION — release state machine and recovery classification.**
    Standardize `BUILT`, `DEPLOYED`, `RELEASED`, `PRODUCTION_VERIFIED` and:
    `SIMPLE_ROLLBACK`, `ROLLBACK_WITH_COMPATIBILITY`, `FORWARD_FIX_PREFERRED`, `IRREVERSIBLE`.

20. **HARDENING — incident mode.**
    For production incidents prioritize:
    `Stabilize -> Contain -> Preserve Evidence -> Diagnose -> Recover -> Verify -> Root Cause -> Prevent Recurrence`.

21. **HARDENING — stop-the-line protocol.**
    Stop affected mutation for unexpected data loss, cross-tenant/boundary leakage, credential exposure, destructive unknown commands, migration corruption, unexplained massive diff, critical security bypass, or repository state that cannot be safely understood.

22. **COMPLETION — durable end-of-task/checkpoint report and unrelated-findings queue.**
    Persist status, changed/why, research, checks, security, data/migration, affected areas, VCS, docs, known issues, not verified, next safe action. Unrelated cleanup/technical debt is recorded separately instead of expanded into the active task.
