## PKG-04 — updater/recovery current-doc delta

Current Tauri v2 updater documentation still requires signed updater artifacts; update signature verification cannot be disabled. The public verification key is distributable, while the private signing key must remain external to repository content/evidence. `createUpdaterArtifacts` remains the v2 artifact-generation switch, and production updater endpoints enforce TLS unless an explicitly dangerous insecure transport option is enabled.

Preplanning consequences:
- preserve one authoritative version/trust model; do not create a second competing updater authority;
- freeze update public-key identity, signed metadata/artifact identity, HTTPS endpoint policy, replay/anti-downgrade semantics and key-rotation/recovery behavior during 04.01–04.03 activation;
- private updater signing material must never be committed, logged, embedded in evidence, or accepted from mutable untrusted code paths;
- negative acceptance must cover invalid signature, wrong key, replayed/older metadata, corrupt/partial artifacts and transport-policy violations;
- Tauri updater adoption remains optional until activation-time reconciliation proves compatibility with the existing `vsn-update` / `vsn-updater-helper` boundary.

Official reference reviewed:
- https://v2.tauri.app/plugin/updater/

## PKG-05 — macOS release current-doc delta

Apple's current direct-distribution guidance continues to require appropriate Developer ID signing for software distributed outside the Mac App Store, Hardened Runtime for notarized apps, secure timestamps, and notarization. Apple documents `notarytool` / Notary API for automated notarization and supports stapling the returned ticket to distributable software.

Preplanning consequences:
- 05.17 must keep Developer ID credentials outside Git/repository artifacts and bind only non-secret signer/notarization identities in evidence;
- exact entitlements and hardened-runtime exceptions must be minimum-scope and activation-time reviewed;
- notarization acceptance must verify submission result/log, ticket/stapling state, final artifact identity and Gatekeeper-relevant signature/notarization properties;
- direct-distribution DMG/app/installer artifacts must remain byte/hash-bound across signing, notarization and stapling evidence so a convenient rebuild cannot silently replace the accepted candidate;
- no macOS signing/notarization secret provisioning is authorized before PKG-05 activation.

Official references reviewed:
- https://developer.apple.com/documentation/security/hardened-runtime
- https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution
- https://developer.apple.com/documentation/security/customizing-the-notarization-workflow

## PKG-05/06 — provenance and supply-chain delta

GitHub artifact attestations continue to use cryptographically signed provenance claims tied to workflow/repository/environment/commit identity and Sigstore infrastructure. GitHub explicitly notes that attestations establish provenance/integrity claims but are not themselves a guarantee that an artifact is secure; policy verification remains required. GitHub also supports attestation verification and lifecycle management.

Preplanning consequences:
- provenance/SBOM evidence must be verified, not merely generated;
- accepted subject digests must equal the exact release artifacts being certified;
- retained attestation/bundle identities and verifier/tool versions should be evidence-bound where offline reconstruction is required;
- deleted/expired/unavailable attestations must not be silently substituted with a differently hashed rebuild;
- security certification should treat provenance as one supply-chain control, not as a replacement for static/dynamic/security testing.

Official references reviewed:
- https://docs.github.com/en/actions/concepts/security/artifact-attestations
- https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations
