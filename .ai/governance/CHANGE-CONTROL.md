# AI Plan Change Control

## Purpose

Approved plans are stable execution contracts. Fresh research may extend them, but an AI agent must never silently rewrite scope, acceptance criteria, security posture or task order while coding.

## Frozen-plan rule

An approved feature plan is identified by feature ID/version, canonical base SHA, plan path, SHA-256 and approval reference in the feature manifest.

After approval:

- do not edit the frozen plan in place to match implementation;
- informational notes may be appended only outside the frozen contract or in a new addendum;
- compatible/material changes create a new plan version or explicit addendum;
- development must verify the recorded plan digest before mutation;
- a digest mismatch is a blocker, not permission to recompute the digest silently.

Accepted legacy v1 manifests/evidence remain valid. Governance V3 does not require retroactive migration. A material change to legacy work is represented through an approved new v2 addendum/work package while the accepted original remains preserved.

## Engineering change classification

Every new v2/work-package contract declares exactly one engineering change classification:

- `CORRECTION`
- `COMPLETION`
- `HARDENING`
- `OPTIMIZATION`
- `NEW_PRODUCT_SCOPE`

`NEW_PRODUCT_SCOPE` requires explicit approval for the new behavior and MUST NOT be auto-implemented. These classifications describe why engineering work exists and are distinct from plan-delta mechanics below and from implementation-gap states.

## Plan-delta mechanics

For change-control decisions, use these mechanics without substituting them for the engineering change classification:

- **Informational** — source/evidence refresh with no behavior, interface, permission, data-flow, acceptance, dependency or rollout impact. Record it; implementation may continue.
- **Compatible extension** — an addition inside already approved product scope that does not invalidate accepted behavior. Requires an approved addendum before implementation when material.
- **Contract change** — modifies interfaces, data flow, permissions, security assumptions, acceptance criteria, dependencies, task ordering, rollout or migration. Requires explicit approval and re-review of impacted downstream stages.
- **Emergency security change** — minimum necessary remediation for actively unsafe behavior. It may interrupt sequencing only when repository security/governance rules permit it, must not opportunistically broaden scope, and requires documented blast radius, recovery and regression evidence.

A compatible extension that is actually new product behavior is still `NEW_PRODUCT_SCOPE` and cannot bypass explicit approval by using a softer delta label.

## Approval scope

For new v2/work-package contracts, approval scope is exactly one of:

- `TASK`
- `MODULE`
- `MILESTONE`
- `PHASE`
- `PROJECT`

Record the approval reference and inherited existing authorization. Inheritance is monotonic (`may_expand=false`): a delegated task, branch, work package or sub-agent may receive only a subset of source authority.

Clearly authorized existing work is not retroactively blocked solely because Governance V3 was adopted. Privileged/external/irreversible actions can still require their own explicit authorization under the applicable trust/release rules; that action-specific approval does not replace the engineering scope vocabulary above.

## Independent approval and mandatory reapproval

The authoring/planning/implementation agent cannot approve its own material plan change, stage skip or privileged external mutation. `approved` is valid only with an independently checkable human/governance decision reference.

A sub-agent cannot approve its parent's change. A textual statement generated by an AI such as “approved” is not approval evidence.

New v2/work-package work requires reapproval when any declared trigger occurs:

- `SCOPE_EXPANSION`
- `PRIVILEGE_EXPANSION`
- `DATA_FLOW_CHANGE`
- `SECURITY_ASSUMPTION_CHANGE`
- `ACCEPTANCE_CHANGE`
- `DEPENDENCY_CHANGE`
- `SHARED_SURFACE_COLLISION`
- `ROLLOUT_CHANGE`
- `IRREVERSIBLE_ACTION`

When a trigger occurs, stop the affected mutation until the changed scope is reviewed. Do not reuse a broader-sounding historical approval as inferred authorization.

## Scope budget and shared surfaces

The approved preflight for new work declares expected paths/modules/change types, shared surfaces/collision keys and a scope budget. Exceeding that budget, touching an undeclared shared surface or discovering a new collision requires `STOP_AND_REASSESS`; if material, reapproval is mandatory.

Scope budgets are safety bounds. They must not be gamed by hiding files, splitting logically atomic work, or moving changes to untracked/unreviewed surfaces.

## Change proposal minimum fields

Each proposal under `.ai/changes/` must contain:

- unique ID and date;
- source feature/plan/version/digest;
- discovery source and research date;
- engineering change classification;
- plan-delta mechanic where useful;
- approval scope and source/inherited authorization;
- triggered reapproval conditions;
- affected stages/files/providers/interfaces/shared surfaces;
- compatibility and migration impact;
- security/data-flow/performance impact;
- acceptance additions/changes;
- disposition: proposed / approved / rejected / deferred;
- independent approver/canonical decision reference;
- new plan/addendum version and digest when approved.

## Stage-skip decisions

`not_applicable` is a governed decision, not a convenience flag. It requires rationale and an independent decision reference. Security and QA cannot be skipped for mutating product work. Data Flow cannot be skipped when files/processes/IPC/network/persistence/secrets/accounts/external services are touched.

## Drift policy

Implementation is drift when it adds behavior not mapped to approved plan/addenda, bypasses a prerequisite stage, broadens permissions/network reach, changes an acceptance denominator, substitutes a different platform/provider, consumes an unmapped starter profile, crosses a forbidden boundary, exceeds the scope budget, collides with an undeclared shared surface, or mutates external state without recorded approval.

Drift must fail planning preflight. Do not normalize it after the fact by editing the plan to match already-written code.

## Platform catalog changes

The platform catalog is intentionally extensible. Adding a provider/profile is normally a compatible extension only when it stays inside approved product scope and:

- uses the provider SDK/declared capability model;
- does not weaken certified templates;
- declares local-vs-SaaS execution accurately;
- maps catalog `starter_profiles` through `.ai/catalog/starter-intents.v1.json` before UI/execution use;
- pins or discovers official tooling safely;
- has explicit secrets/account/network requirements;
- refreshes official market/tooling research at implementation start;
- gets its own acceptance evidence before being advertised as supported.

If the provider/profile itself constitutes new product scope, classify it `NEW_PRODUCT_SCOPE` and obtain explicit approval first. `proposed` does not mean implemented; `existing_certified` is reserved for behavior with repository acceptance evidence.
