# AI Plan Change Control

## Purpose

Approved plans are stable execution contracts. Fresh research may extend them, but an AI agent must never silently rewrite scope, acceptance criteria, security posture or task order while coding.

## Frozen-plan rule

An approved feature plan is identified by feature ID/version, canonical base SHA, plan path, SHA-256 and approval reference in the feature manifest.

After approval:

- do not edit the frozen plan in place to match implementation;
- informational notes may be appended only outside the frozen contract or in a new addendum;
- compatible/material changes create a new plan version or explicit addendum;
- development must verify the recorded plan digest before mutation;
- a digest mismatch is a blocker, not permission to recompute the digest silently.

## Change classes

- **Informational** — source/evidence refresh with no behavior, interface, permission, data-flow, acceptance, dependency or rollout impact. Record it; implementation may continue.
- **Compatible extension** — new optional provider, starter, test or integration that does not invalidate accepted behavior. Requires an approved addendum before implementation.
- **Contract change** — modifies interfaces, data flow, permissions, security assumptions, acceptance criteria, dependencies, task ordering, rollout or migration. Requires explicit approval and re-review of every impacted downstream stage.
- **Emergency security change** — minimum necessary remediation for an actively unsafe behavior. It may interrupt sequencing only when repository security/governance rules permit it. It must not opportunistically broaden scope, and it requires documented blast radius, rollback and regression evidence.

## Independent approval

The authoring/planning/implementation agent cannot approve its own compatible extension, contract change, stage skip or privileged external mutation. `approved` is valid only with an independent human/governance decision reference that can be checked outside the AI-generated artifact.

A sub-agent cannot approve its parent's change. A textual statement generated by an AI such as “approved” is not approval evidence.

## Change proposal minimum fields

Each proposal under `.ai/changes/` must contain:

- unique ID and date;
- source feature/plan/version/digest;
- discovery source and research date;
- problem/new capability;
- change class;
- affected stages/files/providers/interfaces;
- compatibility and migration impact;
- security/data-flow/performance impact;
- acceptance additions/changes;
- disposition: proposed / approved / rejected / deferred;
- independent approver/canonical decision reference;
- new plan/addendum version and digest when approved.

## Stage-skip decisions

`not_applicable` is a governed decision, not a convenience flag. It requires rationale and an independent decision reference. Security and QA cannot be skipped for mutating product work. Data Flow cannot be skipped when any files/processes/IPC/network/persistence/secrets/accounts/external services are touched.

## Drift policy

Implementation is drift when it adds behavior not mapped to the approved plan/addenda, bypasses a prerequisite stage, broadens permissions/network reach, changes an acceptance denominator, substitutes a different platform/provider, consumes an unmapped starter profile, or mutates external state without the recorded approval.

Drift must fail the planning preflight. Do not normalize it after the fact by editing the plan to match already-written code.

## Platform catalog changes

The platform catalog is intentionally extensible. Adding a new provider/profile is normally a compatible extension when it:

- uses the provider SDK/declared capability model;
- does not weaken existing certified templates;
- declares local-vs-SaaS execution accurately;
- treats catalog `starter_profiles` as planning labels and maps them through `.ai/catalog/starter-intents.v1.json` before UI/execution use;
- pins or discovers official tooling safely;
- has explicit secrets/account/network requirements;
- refreshes official market/tooling research at implementation start;
- gets its own acceptance evidence before being advertised as supported.

`proposed` does not mean implemented. `existing_certified` is reserved for behavior with repository acceptance evidence.
